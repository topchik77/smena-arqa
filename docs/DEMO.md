# Сценарий демонстрации

Около 2–3 минут. Откройте клиент и API `/docs`. Для телефона выполните USB-подключение из README.

1. Выберите **1 октября 2026**. Покажите две поездки и контрольные суммы: 3 900 / 585 / 3 315 ₸; наличные 1 500, карта 2 400.
2. Перейдите на 6 октября. Покажите журнал и разбор дня. Без ключа подпись честно говорит «По данным дневника».
3. Выберите пустой день, например 7 октября, и добавьте поездку с выручкой 2 000 ₸, комиссией 300 ₸, временем 08:00–08:20. Сводка должна показать 1 700 ₸ на руки.
4. В `/docs` отправьте `POST /api/v1/trips` с отдельным стабильным ID и повторите то же тело. Первая отправка — `201`, следующая — `200`, количество увеличилось один раз. Измените сумму при прежнем ID — получите `409`.
5. Покажите отказ при окончании до начала или отрицательной сумме. Некорректные записи не добавляются.
6. Объясните сценарий потерянного ответа: клиент сохраняет ID и payload до отправки, сервер защищает уникальность транзакцией. Продемонстрируйте соответствующие автоматические тесты; простое отключение интернета само по себе не доказывает, что сервер успел сохранить поездку.

Не добавляйте демонстрационные записи к 1 октября: этот день удобно сохранять в точном виде из задания. Новые записи постоянны; для полностью отдельной репетиции запустите сервер с другим `ARQA_DB_PATH` и импортируйте JSON туда.

На собеседовании полезно объяснить три решения: почему один снимок нужен для сводки и списка, почему проверка `SELECT` без транзакции не защищает от конкурентных дублей, и почему ИИ не должен считать деньги.
